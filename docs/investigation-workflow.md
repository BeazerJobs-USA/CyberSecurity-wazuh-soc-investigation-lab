# SOC Investigation Workflow & Triage Runbook

## Overview

This runbook defines the structured SOC analyst response protocol for alerts generated by Wazuh File Integrity Monitoring (FIM) targeting OpenSSH server configuration files (`/etc/ssh/sshd_config` and `/etc/ssh/sshd_config.d/*.conf`).

```
+--------------------+      +--------------------+      +--------------------+      +--------------------+      +--------------------+
|  1. DETECTION      | ---> |  2. RULE MATCH     | ---> |  3. SOC TRIAGE     | ---> |  4. HOST AUDIT     | ---> |  5. DISPOSITION    |
|  File Alteration   |      |  Custom Rule 100100|      |  Threat Hunting    |      |  CLI & Forensics   |      |  Evidence-Based    |
|  syscheck inotify  |      |  Severity Level 8  |      |  Events & Context  |      |  sshd -T & auth.log|      |  Triage Decision   |
+--------------------+      +--------------------+      +--------------------+      +--------------------+      +--------------------+
```

---

## 1. Detection Phase: Telemetry Trigger

The OpenSSH daemon controls remote administrative access to Linux hosts. Compromise or unauthorized alteration of this configuration can expose systems to backdoor access, weak cipher suites, root login abuse, or credential sniffing.

- **Monitored Assets:**
  - Primary configuration: `/etc/ssh/sshd_config`
  - Drop-in configuration directory: `/etc/ssh/sshd_config.d/*.conf`
- **Agent Detection Mechanism:**
  - Wazuh `syscheck` module configured with `realtime="yes"` and `report_changes="yes"`.
  - When an inotify event detects a file write, checksum change, or attribute update, a syscheck message is generated and dispatched to the Wazuh manager.
  - Text differences are captured for small configuration files, allowing differential comparison between revisions.

---

## 2. Rule Evaluation Phase: Manager Engine

The Wazuh Manager's `analysisd` engine ingests the syscheck event and evaluates it against parent and child rules:

1. **Parent Match:** Built-in syscheck rule fires based on event action:
   - `550`: Integrity checksum changed (File modified)
   - `554`: File added to monitored directory
   - `553`: File deleted from monitored directory
2. **Child Match:** Custom local rules match the decoded `file` path regex:
   ```regex
   ^/etc/ssh/sshd_config($|\.d/.*)
   ```
3. **Alert Triggered:**
   - Modification -> **Rule 100100** (Severity Level 8)
   - Creation -> **Rule 100101** (Severity Level 7)
   - Deletion -> **Rule 100102** (Severity Level 7)

> **Note on Severity:** Wazuh Level 8 is an operational warning signifying a critical system configuration modification. It does not by itself establish malicious intent.

---

## 3. SOC Triage Phase: Threat Hunting Interface

When Rule 100100 fires, the on-duty analyst executes primary dashboard triage:

```text
Target Filter:
rule.id: 100100 AND agent.name: "vultr-security-lab"
```

### Initial Assessment Checklist:
1. **Event Count & Time Window:** Check if the alert is an isolated event (1 hit) or an ongoing storm of modifications.
2. **Severity Review:** Confirm Rule 100100 is classified as **Level 8** (operational change notification requiring interactive triage).
3. **Payload Inspection:** Expand the alert JSON in the Wazuh dashboard:
   - `syscheck.path`: Verify exact file modified.
   - `syscheck.diff`: Review textual diff showing inserted or removed directives.
   - `syscheck.sha256_before` / `syscheck.sha256_after`: Record hash transition for forensic timeline.
4. **Contextual Expansion:** Open a 24-hour search for `sshd_config` or host activity to observe related administrative or security events (e.g., sudo commands, user logins).

> [!IMPORTANT]
> **Query Filter Scope Warning:**
> Metrics displayed in a dashboard filtered specifically to `rule.id: 100100` (such as authentication failure counters) reflect events associated solely with that query scope. They do NOT establish the absence of authentication failures or brute-force activity across the wider host.

---

## 4. Host-Level Forensic Audit Phase

Real-time FIM alerts identify *what* changed and *when*, but do not record the acting process or user ID (unless who-data auditd mode is enabled). The analyst performs non-destructive host verification via SSH:

### Step 4.1: Syntax Validation
Before any service reload, confirm the syntax is valid:
```bash
sudo sshd -t
```
*Expected result:* Exit code `0` (`sshd -t: OK`). Any syntax error indicates misconfiguration or tampering that could break SSH access.

### Step 4.2: Effective Posture Verification (`sshd -T`)
OpenSSH evaluates configuration directives with **first-value-wins** semantics. Because `/etc/ssh/sshd_config` begins with `Include /etc/ssh/sshd_config.d/*.conf` on modern Ubuntu releases, a drop-in file can override settings without touching the main file. 

Verify the *effective* configuration in memory:
```bash
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication|kbdinteractiveauthentication|permitemptypasswords|maxauthtries|x11forwarding) '
```

Compare output against the approved hardening baseline:
- `permitrootlogin no`
- `pubkeyauthentication yes`
- `passwordauthentication no`
- `permitemptypasswords no`
- `maxauthtries 4`

### Step 4.3: Actor & Authentication Correlation
Correlate the alert timestamp with authentication and authorization logs:
```bash
# Sudo execution logs (identifying who modified the file)
sudo grep -E 'COMMAND=.*(sshd_config|nano|vim|sed|cp|mv)' /var/log/auth.log*

# Active and recent SSH logins around the alert window
sudo journalctl -u ssh --since "2026-10-14 01:30" --until "2026-10-14 02:15"
```

## 5. Disposition & Incident Response Phase

A final disposition should only be assigned once supporting evidence is corroborated:

### Branch A: Expected Administrative Change (Benign Positive)
- **Required Evidence:**
  1. Verified change authorization or operator confirmation matching the alert timestamp.
  2. Sudo execution record in `/var/log/auth.log` identifying the authorized administrator.
  3. Validated runtime posture via `sshd -T` confirming security baselines remain intact.
- **Action:** Record analytical findings, confirm syntax, and document the ticket.

### Branch B: Unauthorized Modification / Suspected Tampering (True Positive)
- **Indicators:** No authorized change record; unexpected directive inserted (e.g., `PermitRootLogin yes`, `PasswordAuthentication yes`); unknown administrative session in `auth.log`.
- **Immediate Containment Actions:**
  1. **Do NOT terminate existing SSH session:** Keep current administrative session open to prevent lockout.
  2. **Preserve Forensic Evidence:** Snapshot memory/state and export Wazuh alert JSON + file diffs.
  3. **Restore Approved Baseline:** Overwrite `/etc/ssh/sshd_config` and clean unauthorized files from `/etc/ssh/sshd_config.d/` using trusted backup or version control.
  4. **Validate Syntax:** Run `sudo sshd -t` before issuing `sudo systemctl reload ssh`.
  5. **Inspect Authorization Artifacts:** Check `~/.ssh/authorized_keys` for unauthorized public keys and inspect `/etc/pam.d/sshd`.
  6. **Isolate Network Access:** Tighten UFW rules to allow connections only from emergency jump host IP.
  7. **Credential Rotation:** Rotate administrative SSH keys and invalidate compromised sessions.
